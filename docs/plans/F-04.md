# F-04 Job queue and worker infrastructure

Guiding rule from review: keep it simple, build only what F-04 needs, write every "change this later" note into the MD files.

## Summary

Add the queue foundation every later async feature uses: a Redis client, BullMQ queues with typed jobs and the default retry and cleanup settings, a worker entrypoint (`src/worker.ts`) with graceful shutdown and job logging, one example no-op job, a repeatable-job helper, and a Redis-backed outbound rate limiter. Also switch `/readyz` to Prisma `SELECT 1` and Redis `PING` (follow-up from ADR 0005), and add the `worker` Compose service.

Refs: JOB-001..015, REL-001, REL-003, REL-004, REL-009, CACHE-011, TD-006, TD-016, SEC-007, SEC-014, PERF-009, PERF-010, DOCKER-006..009, SRD 7.2, 7.3, 22.1, 27, 29.5, 29.13.

Not built: any real queue consumer (email, coding, news, prep-plan, pdf), metrics, bull-board, an HTTP enqueue endpoint, per-queue backoff overrides beyond the defaults, Codeforces "Call limit exceeded" delay handling (F-14).

## Files to create or change

`apps/api` (new)

- `src/lib/redis.ts`: `createRedisClient(config, options)` using `ioredis`. Two flavours: API/readiness client (`enableOfflineQueue: false`, short `commandTimeout`, so `PING` fails fast while Redis is down) and BullMQ client (`maxRetriesPerRequest: null`, which BullMQ requires for workers). Connects lazily so the process starts while Redis is down (DOCKER-009). Logs connection errors at `warn`, rate limited (CACHE-009 style), never the URL (it may hold a password).
- `src/jobs/queues.ts`: queue registry. `QUEUE_NAMES` = the seven names in JOB-011 (`email`, `coding-refresh`, `news-ingest`, `news-summary`, `prep-plan`, `pdf-render`, `maintenance`). Per-queue defaults: `attempts: 3`, `backoff: { type: 'exponential', delay: 5000 }`, `removeOnComplete: { age: 86400 }`, `removeOnFail: { age: 604800 }` (JOB-009, JOB-013).
- `src/jobs/definitions.ts`: typed job definitions. A map `queue -> jobName -> Zod payload schema`; `JobPayload<Q, N>` is inferred from it. F-04 defines only `maintenance/noop`. Payloads hold IDs or small values only (JOB-010). Later features add their entries here.
- `src/jobs/jobQueue.ts`: `createJobQueue({ redis, prefix? })` returns `{ enqueue(queue, name, payload, { jobId?, delayMs? }), upsertRepeatable(queue, name, payload, { every | pattern }, schedulerId), close() }`. `enqueue` validates the payload with the job's Zod schema before it reaches Redis and supports a deterministic `jobId` for deduplication (JOB-006). Services depend on this small interface, not on BullMQ (SRD 7.2).
- `src/jobs/worker.ts` (runner, no process code): `startWorkers({ redis, logger, processors, concurrency, prefix? })` creates one BullMQ `Worker` per queue that has a processor, and returns `close()`. Wraps every processor to validate the payload, create a child logger `{ queue, jobId, jobName, attempt }`, and log start, completion (with `durationMs`) and failure (`warn` when a retry is left, `error` when attempts are exhausted; error and stack only, never the payload). Registers the Worker `error` event so a Redis blip is logged, not thrown.
- `src/jobs/errors.ts`: `NonRetryableJobError` (wraps BullMQ `UnrecoverableError`) so a processor can fail immediately (JOB-009).
- `src/jobs/processors/noop.ts`: the example job `maintenance/noop`, payload `{ message?: string(max 100), delayMs?: int 0..5000 }`. It waits `delayMs`, logs, and returns. The delay exists so the SIGTERM test has an in-flight job; it is capped so a payload cannot hold a worker slot.
- `src/jobs/processors/index.ts`: the `processors` map used by the worker (only `maintenance` now).
- `src/lib/rateLimiter.ts`: `createOutboundLimiter({ redis, name, minIntervalMs, prefix? })` with `acquire({ maxWaitMs? })`. Uses a Redis Lua script registered with `defineCommand` (not `.eval(`, which the `edumetrics.eval` Semgrep rule matches). The script uses the Redis server clock (`TIME`), so API and worker machines need no clock agreement. It stores the next free slot under `ratelimit:outbound:{name}`; each call reserves the slot after the previous one and returns how long to wait. If the wait exceeds `maxWaitMs` it reserves nothing and returns "denied". Request-path callers pass a budget and serve stale data when denied; background callers omit it and wait (CACHE-011). If Redis fails it throws `RateLimiterUnavailableError`; the adapter feature decides the fallback.
- `src/worker.ts`: entrypoint. `loadConfigOrExit()` (never dotenv directly, per PROGRESS FIX-01 note), logger, Redis client, `startWorkers`. On `SIGTERM`/`SIGINT`: `worker.close()` (stop taking jobs, wait for in-flight ones), force exit 1 after 30 s (JOB-014). `unhandledRejection` and `uncaughtException` are logged and exit 1 for the orchestrator to restart (REL-001).
- `src/cli/enqueueNoop.ts`: tiny script that enqueues one `noop` job and exits; used by `compose-smoke.sh` and for manual checks (see ambiguity 1).
- `src/modules/health/health.checks.ts` (+ test): checks become `SELECT 1` through Prisma and `PING` through the API Redis client, same `ReadinessCheck` interface.
- `src/server.ts`: create the Redis client and the job queue, pass them to the readiness checks, close queue, Redis and Prisma on shutdown. Shutdown window goes from 10 s to 15 s (REL-009).
- `src/config/env.ts`, `src/test-utils/config.ts`: `QUEUE_CONCURRENCY_<QUEUE>` for the seven queues (1..50, default 2), exposed as `config.queueConcurrency`.
- `package.json`: dependencies `bullmq`, `ioredis` (exact versions, `ioredis` pinned to the version BullMQ depends on so there is one copy); scripts `dev:worker` (`tsx watch src/worker.ts`), `start:worker` (`node dist/worker.js`).
- Remove `src/lib/tcpProbe.ts` and its test: they become dead code once readiness no longer uses them (see ambiguity 5). First `grep` for every importer of `tcpProbe` and `parseHostPort`; delete only if `health.checks.ts` is the sole user. Record the removal in the feature summary.

Repo root

- `docker-compose.yml`: new `worker` service (same image and bind mounts as `api`, command `npm run dev:worker -w apps/api`, `REDIS_URL` and `DATABASE_URL` overridden like `api`, `stop_grace_period: 35s` so the 30 s drain is not cut short by Compose's 10 s default, healthcheck). Waits for `redis` healthy and `api` healthy (see ambiguity 4), with a short comment in the file saying why (the api container builds `packages/shared` and the Prisma client into the shared bind mount first). Update the file's header comment.
- `.env.example`: the seven `QUEUE_CONCURRENCY_*` variables; fix the comment that says `/readyz` checks TCP only.
- `scripts/compose-smoke.sh`: worker is running and healthy; enqueue via `enqueueNoop` and see the worker log the completion; stopping redis still turns `/readyz` 503 and recovers (existing checks stay). The "every service has a healthcheck" assertion covers `worker`.
- `README.md` (worker and queue notes), `docs/PROGRESS.md` (status, follow-ups), `CLAUDE.md` Commands (`dev:worker`), ADR `0009-queue-and-worker.md` (supersedes the TCP part of ADR 0005; records the decisions below).

`packages/shared`: no change. Job payloads are internal and are not part of the API contract, so their Zod schemas stay in `apps/api/src/jobs` (ambiguity 6). No new error codes.

## Security considerations

| Threat                                                         | Design                                                                                                                                                                                                                                |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Redis exposure and credentials (SEC-007)                       | Redis stays bound to `127.0.0.1` in Compose (F-02). `REDIS_URL` comes from env, can carry a password or use `rediss://`, and is never logged or put in an error message. Production password/TLS is an F-23 item; noted in PROGRESS.  |
| Secrets and personal data in logs and Redis (SEC-014, JOB-010) | Payloads hold IDs only; job logs never print the payload; redaction list unchanged. Failed jobs keep `failedReason` and stack in Redis for 7 days, so processors must not put secrets in error messages (rule written into ADR 0009). |
| Untrusted job input                                            | Every payload is validated with its Zod schema at enqueue and again in the worker before the processor runs; invalid payloads fail as non-retryable. `noop.delayMs` is capped at 5000 ms.                                             |
| Unauthenticated enqueue / queue abuse (SEC-011)                | No HTTP endpoint enqueues jobs. The only enqueue paths are server code and a CLI script run inside the container.                                                                                                                     |
| Denial of service through retries or backlog                   | Retries capped at 3 with exponential backoff; completed and failed jobs are removed after 24 h and 7 d; per-queue concurrency is bounded by env (1..50).                                                                              |
| Job loss or double run on shutdown (JOB-014, JOB-015, REL-009) | `worker.close()` drains in-flight jobs; 30 s hard stop; Compose `stop_grace_period: 35s`. BullMQ re-queues stalled jobs, so processors must be idempotent (written into ADR 0009; the no-op is trivially idempotent).                 |
| Outbound rate-limit bypass or clock skew (CACHE-011)           | One atomic Lua script on the Redis server clock; slot reservation is shared by all processes using the same key; denied calls reserve nothing. Limiter keys are built from code constants, never from user input.                     |
| Redis outage                                                   | API starts without Redis; `/readyz` goes 503; enqueue throws a typed error that services map to 503 (the real mapping is added with the first caller); worker reconnects. Redis is not a source of truth (ED-002).                    |
| Injection                                                      | No string-built commands; Lua script is a fixed constant with arguments passed as parameters; no `eval(` in our source (Semgrep rule); `Math.random` not used (job IDs from `crypto.randomUUID`).                                     |
| Object-injection lint (eslint-plugin-security)                 | Queue and job lookups use typed `Map`s or explicit `switch`, not dynamic `obj[userKey]`.                                                                                                                                              |
| Supply chain (SEC-021)                                         | Exact-pinned `bullmq` and `ioredis`; `npm audit` right after install; a high or critical finding stops work and is reported, no ignores.                                                                                              |
| Scanner suppression                                            | None added.                                                                                                                                                                                                                           |
| bull-board exposure (SRD 21)                                   | Not added; it is optional and would add a dependency and an HTTP surface.                                                                                                                                                             |

## SRD ambiguities and proposed resolutions (simple choices)

Review decisions (confirmed by owner): 1 no HTTP enqueue endpoint, proven by integration tests and the in-container script; 2 delete `tcpProbe.ts` and its tests after confirming nothing else imports it, and note the removal in the feature summary; 4 worker waits for `api` healthy, with a short explanatory comment in `docker-compose.yml`; 2 (queue scope) concurrency variables for all seven queues, workers only for `maintenance`.

1. **"API can enqueue a job"** with no endpoint in the SRD catalog. Proposed: no HTTP endpoint (an unauthenticated enqueue route would be abuse-prone and the catalog says none exists). The API process owns the queue producer (`createJobQueue`), proven by integration tests and by a CLI script, `src/cli/enqueueNoop.ts`, run inside the api container in `compose-smoke.sh`. Real enqueuing arrives with the first feature that needs it (F-08 email).
2. **Queue and concurrency scope.** JOB-011 lists seven queues and JOB-012 wants a concurrency variable per queue, but only the no-op job exists. Proposed: register all seven names and their env variables now (cheap, SRD 22.1 lists them), start workers only for queues that have a processor (only `maintenance`), default concurrency 2.
3. **"Repeatable jobs" vs BullMQ's current API.** BullMQ replaced `add(..., { repeat })` with job schedulers (`upsertJobScheduler`), which are idempotent by scheduler id. Proposed: use job schedulers; same behaviour as TD-006 intends.
4. **Worker Compose dependencies.** DOCKER-009 says services wait for dependencies, but the worker only needs Redis now. The Compose bind mount hides the built `packages/shared` and generated Prisma client, and the `api` service's `npm run dev` creates them; two containers doing it at once could race. Proposed: worker waits for `redis` healthy and `api` healthy, and runs `tsx watch` directly. Revisit when the production image exists (F-23). Worker healthcheck is a simple process check (DOCKER-008 lists none for the worker; the smoke script requires one).
5. **Removing `tcpProbe`.** It has no user after the `/readyz` change. Proposed: delete the file and its tests as dead code (this removes tests, so flagging it per CLAUDE.md; the behaviour they covered moves to the new `health.checks.test.ts`). If you prefer, keep it and I only change the checks.
6. **Job payload schemas location.** CLAUDE.md puts shared Zod schemas in `packages/shared`; job payloads are internal to the api/worker (same package). Proposed: keep them in `apps/api/src/jobs/definitions.ts`; move only if the web app ever needs them.
7. **Codeforces "Call limit exceeded" retry with at least 2 s delay (JOB-009).** Needs a Codeforces adapter, which does not exist. Proposed: out of F-04; the `NonRetryableJobError` / normal-throw split and the exponential backoff give F-14 the hooks; noted in PROGRESS.
8. **Readiness reconnect.** ADR 0005 chose a fresh TCP connection so nothing needs reconnecting. Prisma's pool and ioredis reconnect on their own, but this must be proven again: the existing smoke checks (MySQL/Redis stop, 503, recover to 200 with no api restart) are the proof. If Prisma's pool does not recover, fall back to a fresh short-lived check connection for MySQL and report it.
9. **Metrics (Section 21: queue depth, limiter waits).** Not in F-04's scope or acceptance; left for the observability work in F-23.

No deviation from the SRD that needs an ADR other than the ADR 0009 that records the choices above.

## Future notes to write into docs (so later features do not suffer)

To go in `docs/PROGRESS.md` "Known gaps / follow-ups" and ADR 0009:

- Every processor must be idempotent (JOB-015), use a deterministic `jobId` when a job must not run twice, keep payloads to IDs, and never put secrets or personal data in error messages (failed jobs keep them for 7 days).
- New job: add the queue name if needed, add its payload schema to `jobs/definitions.ts`, add the processor to `jobs/processors/index.ts`.
- Worker dependencies (Prisma, email sender, adapters) are passed into `startWorkers`/processors by `src/worker.ts`; F-08 is the first to need Prisma there, and will add `depends_on: migrate`/`mysql` to the `worker` service.
- F-14/F-15: use `createOutboundLimiter` with names `codeforces` and `leetcode`, intervals from `CODEFORCES_MIN_INTERVAL_MS` / `LEETCODE_MIN_INTERVAL_MS`; request path passes `maxWaitMs`, workers do not. Codeforces "Call limit exceeded" needs a retry delay of at least 2 s.
- F-05: rate limiting (SEC-016) needs its own Redis-backed limiter with an in-memory fallback; F-04's outbound limiter is not that.
- F-23: Redis password/TLS in production, AOF to keep queued jobs across restarts (DOCKER-005), worker production image command `start:worker`, metrics (queue depth, limiter waits), `NODE_ENV=production` reminders already noted.
- Integration tests: unique key prefix per run, never `FLUSHALL`.

# F-03 Database foundation

Guiding rule from review: keep every ambiguity simple, build only what F-03 needs, keep all tests passing, and write every "change or delete this later" note into the MD files (PROGRESS.md follow-ups, ADR 0007) so later features are not surprised.

## Summary

Add Prisma with MySQL 8 and one migration for the five identity tables (`User`, `OAuthAccount`, `Session`, `AuthToken`, `StudentProfile`). Add the minimum plumbing later features reuse: a Prisma client lifecycle, a transaction helper, one repository as the pattern example, and an idempotent seed with a dev-only demo student. `prisma migrate dev` and `migrate deploy` work in Compose.

Refs: DB-001..008, TD-013..015, AUTH-004, USER-003, SEC-005, SEC-008, SEC-010, SEC-014, SEC-022, DOCKER-009, DOCKER-011, REL-006, SRD 7.2, 7.3, 12, 27, 29.16.

Not built: endpoints, hashing, Redis client, any other table, `/readyz` change (deferred to F-04, see Future notes).

## Compose design

- `migrate`: one-shot, same dev image, `npm run db:migrate:deploy`, `restart: "no"`, waits for mysql healthy. `api` uses `depends_on: migrate: service_completed_successfully`. Satisfies DOCKER-011 and makes a clean `docker compose up` produce tables. `api` still does not wait for leetcode-api.
- Developer commands (README): `docker compose run --rm api npm run db:migrate:dev -- --name <name>`, `docker compose run --rm api npm run db:seed`.
- Init script grants only Prisma's shadow-DB name pattern (`prisma_migrate_shadow_db_%`) to the app user. Runs on first volume creation only, so existing dev volumes need `docker compose down -v` once.

## Security considerations

| Threat                                          | Design                                                                                                                                               |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQL injection (SEC-010, DB-007)                 | Prisma only; architecture test bans `*Unsafe` raw calls.                                                                                             |
| IDOR (SEC-008, SEC-022, DB-001, CONV-005)       | Owned-data repository methods require `userId`; cascade FKs leave no orphans; later features copy the pattern.                                       |
| Token and password storage (AUTH-004)           | Only hash columns exist; test asserts no plaintext column.                                                                                           |
| Secrets and logs (SEC-005, SEC-014, DOCKER-003) | `DATABASE_URL` from env only; Prisma log level `warn`/`error` only (never `query`, it would log emails and hashes); parse errors never echo the URL. |
| Wiping a dev DB from tests                      | `_test` name guard.                                                                                                                                  |
| Over-privileged DB user                         | ALL only on its own DB plus the shadow-DB pattern, dev only. No `*.*`.                                                                               |
| Demo account in production (DB-008)             | Seed refuses in production; demo user has no password.                                                                                               |
| Non-TLS DB connection                           | `allowPublicKeyRetrieval` only outside production; production TLS is F-23.                                                                           |
| Timestamp corruption (TD-014)                   | UTC round-trip test under a non-UTC `TZ`.                                                                                                            |
| Supply chain (SEC-021)                          | Exact-pinned Prisma 7.10.0. `npm audit` right after install; a high or critical finding stops work and is reported, no ignores.                      |
| Scanner suppression                             | None added.                                                                                                                                          |

## SRD ambiguities and proposed resolutions (simple choices)

1. **Prisma version.** `latest` on npm is 8.0.0-rc.19 (release candidate). Use stable 7.10.0 with the MariaDB adapter (required by Prisma 7, supports MySQL 8).
2. **Required profile fields vs two-step registration.** Registration gives only `fullName`; academic fields are nullable in the DB, and F-09's Zod schema makes them required. `onboardingCompletedAt IS NULL` means pending. Range rules (semester 1-16, scale 4.0-10.0) stay in Zod.
3. **Seed location and demo login.** Seed code lives in `src/db/seed/` (the SRD's `prisma/seed.ts` is outside the tsconfig, so lint would skip it). Demo student has a verified email, a finished profile and no password, since hashing arrives in F-05 and adding a dependency now breaks scope. F-05 sets the password.
4. **Shadow DB for `migrate dev`.** Init-script grant limited to the shadow-DB name pattern.
5. **Migration timing.** One-shot `migrate` service, not inside api start.
6. **Test DB selection.** `_test` name guard with compose fallback; no new env var.
7. **IDs.** UUID v7 as `CHAR(36)`.
8. **`Session.replacedById`.** Plain column now.
9. **DB connect retry (DOCKER-009).** Prisma connects lazily and its pool reconnects; no retry loop.
10. **`/readyz` MySQL check.** Stays a TCP probe; switching to `SELECT 1` moves to F-04 (it touches the same check list as Redis `PING`).

Decision 3 and 10 deviate from what earlier notes suggested; please confirm.
